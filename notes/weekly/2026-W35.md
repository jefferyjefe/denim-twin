## Review questions
- **What measurable uncertainty did we reduce?** Whether the 2D pipeline can reproduce a real cut automatically:
  yes on the one usable found pair (sil IoU ~0.8–0.88 vs 0.35 no-op). Whether v0/v1 fray rendering predicts a real
  fringe: no — indistinguishable from crop-only at found-image resolution (fringe IoU 0.07). Whether found tutorial
  pairs are a viable data source: mostly no (1/14 usable).
- **Which assumption failed?** (1) That tutorial pages give paired whole-garment photos — most are crops/worn/macros.
  (2) That identity metrics were informative — a no-op aced them until real after-captures + null baselines existed.
  (3) That an in-sample TPS residual meant anything (leave-one-out: 158 px). (4) That cloud routines would run —
  every run stalls after "Claude Code process started", including a no-tool smoke test.
- **Physical matching improved, or only attractiveness?** Cut geometry: physical matching (measured). Fringe: only
  attractiveness so far; the honest fringe IoU is 0.07.
- **Next experiment tests one hypothesis?** Yes: "with ≥5 usable pairs, a fringe-depth/coverage model fitted on
  after-wash hems beats crop-only on fringe IoU and profile distance on held-out pairs."
- **Reproducible?** 44 tests; run_pair.py is one command per pair; batch + report scripts; pair images are research-use
  only and not redistributed. Not yet verified on a fresh machine (repro runner never ran).
- **Scope expanding without evidence?** No 3D/mesh/learned work. Online-only variant is a charter amendment (owner
  decision) that narrows the claim. Scope check: gate_0 only.

## Addendum — Sat 2026-08-29 (day session)

**Built**
- `canon/wash.py`: procedural wash appearance v0 — anisotropic shrinkage, hem-roll shading, dye loss; conservative /
  median / aggressive presets; `none` byte-identical. Off by default (`run_pair --wash`, `PAIRS_WASH=`).
- `eval/identity.align_to_reference` / `aligned_identity`: identity judged after a **bounded affine** alignment
  (mask moments + ECC, every axis scale clipped to ±15%), so a legitimate shrink is no longer scored as identity loss.
- `tools/predict.py`: the product path — one photo + a cut spec → three renders, an 80% fringe interval,
  `modification.json`, `diff.png`, `prediction.json`. This is the first code that answers the thesis question for a
  garment with no after-photo.
- `tools/score_predict.py`, `tools/ingest_unpaired.py` (evidence-gated unpaired after-wash channel).

**Learned (all negative or deflationary, which is the point)**
- Shrinkage cannot be measured from found photos: landmark noise on re-laid garments is ~50× the 1–3% signal (EXP_0013).
- Our shrinkage anisotropy has **no verified source** — the one measurement paper we could read (Talu 2021) is
  industrial roll washing and if anything shows the opposite ordering (EXP_0013 Part D, LITERATURE 14).
- The product path scores **0.767** mean silhouette IoU where the evaluation path (which reads the real after-photo)
  scores 0.819; README now quotes the former (EXP_0014).
- `inseam_fraction` means different things in `run_pair` (image space) and `modification.py` (canonical), differing by
  up to 0.21 of the leg — a real bug, fix pending review.
- A single global cut angle adds nothing; per-leg polylines would be needed.

**Next**: triage the fourth adversarial review; fix the inseam-fraction definition; ingest whatever the unpaired
after-wash harvest returns and refit the prior. Everything else is still gated on contributed pairs.

## Addendum 2 — Sat 2026-08-29 (afternoon): two corrections that matter more than the features

**Fourth adversarial review found 8 code bugs and 6 documentation overclaims — all fixed, all tests adopted (107 + 1
xfail, CI green).** The two that changed conclusions:
- `apply_cut` had been collapsing every canonical cut mask to its topmost row, so **no angled cut was ever applied**.
  EXP_0014's "a cut angle buys nothing" was a null result about code that ignored the angle; re-measured, the angle
  helps slightly (0.768 → 0.772 IoU) and the sign is now meaningful.
- `run_pair --wash` had been reassigning the masks that define the null baselines, so EXP_0013's A/B was scored against
  a moving reference. Pinned; both batches re-run. The corrected table says procedural wash v0 **does not improve any
  metric and hurts fringe overlap** — the earlier "better on 10/11" was the artefact.

**EXP_0015 — the fringe has never actually been measured.** SAM's prompted "fringe" mask returns the bottom third of
the fabric (0.10–0.61 of waist width; visible in `reports/fringe_methods/sheet_*.jpg`). A new direct thread measurement
paints the right pixels and recovers known depths to ±2 px on synthetics — but scores **cuffed hems (0.0081) the same
as frayed ones (0.0077)**, because at flat-lay resolution the fringe is a few pixels and so is our outline error. Every
fringe number in the repo predates that control, including EXP_0008's held-out comparison. All channels were rebuilt on
the one method; the prior now carries `validated: false` and the control result as fields, `predict.py` says the depth
is a placeholder, and a sub-resolution interval is flagged rather than shown as three near-identical pictures.

**Consequence for the ask:** the single most valuable thing a contributor can send is now **one close-up of the hem
with the coin in frame**. The issue form and CONTRIBUTING_PAIRS.md say so, with the reason.
